# Monorepo 与私服架构迁移计划

状态：待实施。设计基线见 [目标架构](../architecture/target-design.md)，验收见 [私服联调](registry-integration.md)。

## 原则

本仓库现行 0.2.12 为可用基线，先增加目标文档、再分阶段迁移。保留现有可运行功能、真实 DSH dev 启动、测试、回滚及离线卸载；不提前删除旧分发服务。源码迁移不等于必须兼容所有历史目录，但在公司实际安装旧版本的情况明确之前，提供明确的升级/迁移或重装路径，不破坏已装能力、手动包和用户数据。旧路径只在新路径验收后移除。

## 并行工作

- A 私服部署（部署者）：Mac mini 配置 npm/PyPI/Raw、准备测试依赖、确认访问及证书；输出非敏感连接信息。
- B 代码准备：不依赖真实私服即可完成 workspace 边界、协议和 mock、管理端 MVP 骨架、终端同步及原生 adapter 抽象。
- C 联调：A/B 接口就绪后验证真实 DSH，按实验结果完善 adapter，先 Mac 再 Windows。不存在已在后台自动运行的工作；以仓库提交与验收记录为事实。

## 阶段与交付门禁

| 阶段 | 工作 | 验收 |
| --- | --- | --- |
| M0 | 文档、现有基线梳理、确定 workspace 与私服合同 | 产品/架构/验证说明一致，区分现状/目标 |
| M1 | pnpm workspace、根脚本、移动终端与官方能力（独立 package/version），保留构建兼容入口 | 现有测试通过；真实 dev 启动；CI 仍可构建旧包；无无关重写 |

| M3 | 管理端单体 MVP：认证授权、私服引用解析、草稿、发布/下架/撤回、审计、公开只读目录 | 多能力独立发布、失败不推进 revision；普通用户无写权限；备份恢复 |
| M4 | 终端本地同步服务与 npm Bundle adapter；状态缓存及 UI 通知 | mock 测试与 V01–V03、V09、V11；原生安装状态/失败恢复真实核验 |

M2/M3/M4 可在 M1 确立公共协议后并行；Python、MCP 和资源 adapter 可以独立开发，真实宿主结果仍是最终门禁。避免同时改动账本、宿主安装逻辑和 UI 导致难以定位。现有的 build.mjs 全量生成 catalog/包的逻辑须拆成独立发布命令，旧离线 ZIP 作为过渡或可选导入方式，而非正式内网主路径。

## 开发约定

- 根命令最终统一 pnpm dev / build / test / typecheck，支持按 workspace filter 独立运行；admin 与终端插件分别可启动，联调通过固定或显式传入地址。
- 官方能力独立 package.json / version / metadata / tests / changelog；非 npm 制品独立版本与 lock。GenUI 等未改上游包以 provenance 引用维护。
- 管理端发布 API 和终端读目录使用共同 schema；管理端 API 不暴露制品上传凭据；核心索引独立。
- 安装执行仅在本机插件服务；UI 不持有管理员凭据或执行任意命令；操作/同步日志脱敏。
- 现有 tests/core、service、release、ui、office 等覆盖必须随迁移保留或等价替换；新增无公网空缓存集成测试。
- 提交使用 Conventional Commits 中文描述；阶段拆分提交；不在尚未验收时发布正式版本。

## 完成定义

开发者在独立官方或第三方仓库发布一个支持类型的能力并提交上架，无需修改或重新发布中心；已安装 DSH 的用户在下一次成功同步发现它并可安装、使用、更新和卸载；依赖从内网私服解析，普通依赖不出现在市场；任何安装失败要么经验证回滚，要么明确锁定并提供恢复信息。管理端、终端、能力包独立版本、发布、部署。
